## 3. Where the OFO list came from, and how it is stored

From the official DHET master workbook you supplied (`docs/OFO-Codes-2021.xlsx`),
transcribed by script, never retyped. Loaded and verified live: **8 major
groups, 40 sub-major groups, 125 minor groups, 440 unit groups, 1,511
occupations** with their six-digit codes as text, and **5,946 specialisations**
as the synonym layer. Every level carries a foreign key to its parent and the
seed fails loudly on any orphan or count drift.

Two source anomalies, both logged by the generator and handled deliberately:
- Sub-major group 62 is missing from the workbook's own summary sheets while
  seven real occupations (Tree Feller through Hunter) sit under it. It was
  repaired with its ISCO-08 title, the one row not transcribed from the
  workbook.
- 22 specialisation rows point at occupations that do not exist in OFO 2021
  (one is literally titled "Mine Ventilation Officer: DELETED"). They were
  dropped rather than inventing parent occupations; the full list is printed
  by `scripts/seed-ofo-2021.mjs` on every run.

## 4. How an unrelated skill is structurally impossible

Every row in `jobs_ofo_skills` has a foreign key to exactly one sub-major
group. The skills endpoint derives the group from the chosen occupation's
code prefix and queries only those groups. Proven live with SQL: zero
"Bricklaying" rows under sales' branch, zero skills without a branch, all 40
branches populated. Free-text skills are stored separately in the person's
own `skills` list and never used for matching.

## 5. What the parser extracts, discards, and how no-file-stored was proven

Extracts: name, phone, suburb, province, years, summary, up to 12 skills, up
to 10 work history entries, and an occupation hint. Discards: the file itself
(parsed in request memory, never written to disk or storage; there is no
storage call anywhere in the import path), ID numbers and bank-account-like
digit runs (stripped from the raw text BEFORE the model sees it, and again on
every output field). Proven with a generated .docx carrying a planted ID
number: every field came back exactly as written and the ID appeared nowhere.
Parsing failure returns a plain message pointing at the guided build.

## 6. AI caps and cost per CV

Model: `claude-sonnet-5` for all four AI paths, not the cheapest model,
because this repo's own live testing (recorded in `lib/ai/draft-copy.ts`)
caught Haiku fabricating facts twice, and a fabricated claim on a CV can cost
someone a job. Anti-fabrication is enforced three ways: restate-only prompts,
an invented-year rejection check, and (for import) the pre-model ID strip.

Caps: **3 Write-with-AI turns per CV** and **3 wording checks per CV**, only
successful calls spend a turn, and generated drafts are stored so redisplay
never re-runs the model. CV import is Turnstile-gated plus 5 uploads per IP
per hour. The employer's advert tidy is 10 per account per day (employers are
the paying side).

Estimated cost per CV at standard Sonnet pricing: about R0.10 per AI call,
so roughly R0.30 if someone uses all their writing turns, and about R1.00
worst case if one CV uses every writing turn, every polish check, and an
import. Typical will be far lower.

## 10. Found and deliberately not fixed

- The old `jobs_taxonomy` table is still in the database and one migration
  seeds it. Nothing reads it any more, but dropping a table is a
  deleting-something-shared decision: say the word and it goes in one small
  migration.
- The vacancies browse "type of work" dropdown uses the 40 official
  sub-major group names, which read formally ("Building and Related Trades
  Workers"). Friendlier display names would be another curated list; not
  done now to keep launch scope honest.
- The listing counter and "days remaining and one-tap renew" the handoff
  wanted on the seeker dashboard: candidate listings do not expire in this
  build (see 11), so there is nothing to count down or renew. The dashboard
  shows listed/not-listed with the one-tap switch instead.
- In-memory rate limits still reset per serverless instance (documented
  before); the durable anti-scrape control remains the view log watchlist.
- Held vacancies keep their spent free post even if you later remove them in
  admin. Deliberate: an unheld retry must not be a free retry.

## 11. Where the brief was wrong about the code

- "Listing status: with the days remaining and a one-tap renew" (Job 5):
  candidate listings never had an expiry; only vacancies do. Building
  candidate listing expiry would be new scope with its own purge rules, so
  the dashboard tells the truth about what exists instead.
- "Applicants per job, with status per applicant" (Job 7) implied an apply
  flow, which did not exist anywhere; it was Sprint 3 scope pulled forward
  and is now built (that is what `jobs_applications` is).
- The handoff's walkthrough note that completing the flow "drops the person
  on the home screen": it actually dropped them on the review screen; either
  way it now lands on the dashboard.

## Slow-query flags for scale

- Occupation search is ILIKE over titles and 5,946 synonyms, backed by
  trigram GIN indexes; fine for a long time.
- Browse filtering uses a `like '64%'` prefix over `ofo_occupation_code`.
  On a large CV table that wants a btree on the code column (it exists:
  `jobs_candidates_ofo` / `jobs_vacancies_ofo`), prefix LIKE uses it.
- The seeker dashboard's alerts query does an OR of prefix matches; if it
  ever slows, materialise the sub-major code as its own column.
